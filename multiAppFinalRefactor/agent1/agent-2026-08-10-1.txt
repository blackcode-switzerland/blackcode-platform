--- Bug #1, found and fixed: verify.sh crashed silently on connection failure ---
First run of case (f) printed NOTHING and exited 2 — not the intended clean
"ERROR: could not connect..." and exit 1. Root cause: `set -euo pipefail` at
the top of verify.sh, combined with `out="$(... | db_run "$url" 2>&1)"` inside
db_check_connection — a failing command substitution inside a plain assignment
trips `set -e` immediately, before the function's own error-handling code (the
`if [ $rc -ne 0 ]...` block) ever runs. The intended error message never
printed. Fixed by wrapping every such capture in lib-db.sh
(db_check_connection, db_current_database, and the three internal queries in
db_capture_stats) with `set +e` / `set -e` pairs, and by wrapping the two call
sites in capture-baseline.sh and verify.sh that assign db_capture_stats's
output. Re-tested after the fix — see the table above, all (f) cases now fail
loudly with a clear message.

--- Bug #2, found and fixed: file-role tracking broke on an empty declarations file ---
First real run of verify.sh (clean baseline, no EXPECTED declarations at all —
the normal case for Phase 0) reported ALL 49 tables as "MISSING from the
database" while also claiming 49 tables live — total nonsense, and it would
have been the very first thing the next six agents saw from this tool. Root
cause: verify-diff.awk originally tracked which of its three input files
(declarations / baseline / live) it was reading by counting FNR==1 events. The
declarations file is legitimately EMPTY on a normal run — no line in it ever
triggers FNR==1 — so the counter never advanced past 0, and the baseline
file's first line was read as if it were the declarations file, live data as
if it were the baseline, and the real live data was never read as live data at
all. Every table looked baseline-only. This is worth naming explicitly: it is
the same *shape* as CLAUDE.md finding #5 (a check that silently measures less,
or the wrong thing, than it claims) but inverted — instead of a false PASS, it
produced a false, total, RED. A red-when-it-shouldn't-be is much easier to
notice than a false green, which is presumably why it surfaced this fast — but
it would still have cost the next agent real time debugging a "database"
that appeared to have lost everything. Fixed by matching each input line's
FILENAME against the actual paths (passed in via `-v declfile=... -v
basefile=... -v livefile=...`) instead of counting reads. Re-verified clean
immediately after.

3. WHAT THIS LEDGER CANNOT CATCH — BE SPECIFIC
================================================================================
Ordered by how much I think each one matters:

1. **Right count, wrong rows.** This is the sharpest gap and worth stating
   plainly: verify.sh confirms HOW MANY rows a table has and the SHAPE of its
   id range. It does not confirm WHICH rows. A bug that deletes exactly the
   number of rows a declaration expects, but the WRONG rows (e.g. Phase 3's
   sales-only delete accidentally matches some issues rows too, netting the
   same row count as the sales-only delete would have), passes clean. This is
   exactly why SAFETY.md's "run the SELECT form first and read the count, read
   the DELETE count, then COMMIT" steps are not redundant with verify.sh —
   they're the identity check; this ledger is the magnitude-and-omission
   check. Say this to whoever runs Phase 3: verify.sh passing does not mean
   the right 8 rows went, only that 8 went and were declared.

2. **No content corruption detection.** An UPDATE that blanks out, corrupts,
   or silently truncates a column (e.g. a bad migration nulling every
   comment's body) changes nothing this ledger looks at — count, min(id) and
   max(id) are all unaffected. Out of scope for a shell+SQL, no-new-dependency
   tool without per-row checksums, which nobody asked for, but worth writing
   down rather than letting the ledger's coverage look bigger than it is.

3. **The min/max mechanism assumes monotonically-assigned ids.** It works
   because Postgres `serial`/identity columns hand out ever-increasing values,
   so a genuine delete-and-insert always moves the extremes. A table using
   externally-supplied, non-monotonic, or resettable ids would defeat this —
   not present in this schema today (checked: every integer `id` column here
   is a `nextval(...)` sequence default), but worth a note if a future app or
   migration introduces one.

4. **Batched query, not per-table isolation.** db_capture_stats builds ONE big
   UNION ALL across every table and runs it in a single round trip (fast, and
   avoids the N-round-trip alternative). This means a permissions problem on
   ANY single table — e.g. running this as the bounded `issues_app` role
   instead of `MIGRATE_DATABASE_URL` — would fail the ENTIRE capture/verify
   run with one Postgres error, not degrade to "48 tables checked, 1 access
   denied." I did not test this against a restricted role; SAFETY.md already
   says migrations run as `MIGRATE_DATABASE_URL`, and I'm making explicit here
   that baseline/verify should follow the same rule for the same reason —
   worth a one-line addition next time SAFETY.md gets touched, not something I
   added since it's not what this phase's code needs to do (both scripts
   already work correctly under the owner role I tested with).

5. **The adversarial "reset the sequence and refill" case is unfalsifiable by
   design.** If a table were TRUNCATEd and refilled with fabricated rows whose
   ids happen to span the exact same [min, max] range as the originals, with
   the same final count, this ledger cannot tell the difference — no
   count/min/max-only check can. Only a per-row content hash would, which is
   out of scope here. I did not attempt to build or fake this scenario locally
   since it requires no real assertion to write down as untested — it's a
   structural limit of the approach, not a bug to chase.

6. **Only schemas platform/issues/sales, only BASE TABLEs.** `drizzle` (the
   migration-history schema) and `public` are not tracked; neither are views.
   Not required by the brief and not a data-loss surface issues/sales users
   would notice, but naming it so nobody assumes coverage that isn't there.
