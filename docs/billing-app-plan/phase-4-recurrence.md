# Phase 4: Recurrence

**Goal:** a bill that repeats on an agreed schedule for an agreed number of
times, generated by an agent, with double-billing made structurally impossible.

- **The problem** — most of the retainer work is billed on the same terms every
  quarter, and retyping it is both tedious and a source of transcription errors.
  The obvious implementation is a scheduler inside the app, and it is the wrong
  one twice over: this platform's apps contain no intelligence and run no jobs,
  and an open-ended recurrence is a standing instruction to invoice somebody
  forever that nobody remembers agreeing to. There is also a specific failure to
  design out: an agent that retries a generation it already completed would
  issue a second real bill for the same period, and the client would receive two
  demands for one thing.
- **What this phase does** — stores a rule as data: a frequency, a start date and
  an **occurrence count** that is the end condition, plus a counter and the next
  date. Nothing in the app fires on that date; an agent reads it and calls one
  endpoint, which creates the next occurrence as an ordinary draft through the
  ordinary create path. Idempotency is a partial unique index on
  `(recurrence_id, occurrence_period)`, so a second call for the same period is a
  409 from Postgres rather than a second invoice.
- **Expected result** — `bk billing recurrence list --due` names the rules whose
  next date has arrived; `bk billing recurrence generate <seq> --period 2026-10`
  produces one draft with the next number in the sequence; calling it twice for
  the same period produces a 409 naming the invoice that already exists; a
  series stops at its cap and marks itself completed; and no code path anywhere
  in the app schedules anything.

## In one look

| | |
|---|---|
| **Data** | Rules such as "bill this same thing every quarter, eight times, then stop", how many have been issued, and which period each generated invoice belongs to. |

#### The idempotency index — the whole point of the phase

```sql
CREATE UNIQUE INDEX uq_invoice_occurrence
  ON billing.invoice (recurrence_id, occurrence_period)
  WHERE recurrence_id IS NOT NULL
    AND occurrence_period IS NOT NULL
    AND status <> 'void';
```

Two facts are encoded in the `WHERE`, and both are decisions:

- **A retrying agent cannot double-bill.** The second insert for a period
  violates the index and `pgViolation` in `packages/platform-api/src/handler.ts`
  turns `23505` into a `409 already_exists` with a suggestion. The route does not
  check first — a check-then-insert is a race, and the index is the only thing
  that can settle it.
- **`status <> 'void'` means a cancelled occurrence does not consume its
  period.** That is position **P7**: the mockup's BC-2026-0033 was voided and
  BC-2026-0034 replaced it, and together they are **one** occurrence of the Junod
  series. So a void frees the period for a replacement while still keeping its
  own invoice number consumed forever. The two behaviours are different and both
  are deliberate.

### `lib/derive/recurrence.ts`

Pure, and all three functions are date arithmetic on strings:

```
periodKey(frequency, date)      → '2026-10' | '2026-Q4' | '2026'
nextDate(frequency, from)       → the next date, same day-of-month where it exists
isComplete(rule)                → occurrences_done >= occurrences_total
isDue(rule, today)              → status === 'active' && next_date <= today
```

**`nextDate` has one trap worth a test:** a monthly series starting on the 31st.
Clamp to the last day of the shorter month and stay clamped to the original
day-of-month afterwards, rather than drifting to the 28th forever. Test January
31 through to March.

### The generation endpoint

`POST …/recurrences/{seq}/generate`, body `{period}`, one transaction:

1. Load the rule. Refuse if `paused` or `completed`, with a suggestion naming
   `bk billing recurrence resume`.
2. Refuse if `period` is not the rule's expected next period — a typo'd period
   would otherwise create a bill for a quarter nobody asked for. **Refuse, do
   not substitute**: this is the subject-parameter rule, and a substitution here
   is a real invoice.
3. Copy the template through the ordinary `createInvoice` path, so an occurrence
   is an ordinary draft with the next number from the company's sequence, the
   template's lines, client block, VAT rate, currency and language, and dates
   computed from the period.
4. Increment `occurrences_done`, recompute `next_date`, and set `completed` with
   `next_date = null` if the cap is now reached.
5. Two audit rows: `created` on the invoice, `field_changed` on the rule.

Steps 3 and 4 are **one transaction with the invoice insert.** A counter that
advanced without an invoice, or an invoice without an advanced counter, are both
states that produce a wrong bill next time.

`generate` also honours `Idempotency-Key` ([`integration-surface.md`](integration-surface.md)
§2). The two mechanisms answer different questions: the index above is what
makes a retry **safe**, and the key is what makes it **quiet**. A retried call
with the same key gets the same 201 and the same invoice back; only a call with
a fresh key for an already-generated period gets the 409 it has to interpret.

**The app schedules nothing.** There is no cron, no queue, no `setInterval`, and
`TECH-STACK.md` constraint 8 says the stack must not tempt anyone into one.
`bk billing recurrence list --due` is the whole discovery mechanism, and an agent
outside the app is what calls it.

## Routes and CLI

| Route | Command |
|---|---|
| `GET /api/workspaces/{ws}/recurrences` (`?company= ?due=`) | `bk billing recurrence list [--due]` |
| `POST /api/workspaces/{ws}/recurrences` | `bk billing recurrence create --template <ref> --frequency quarterly --start 2026-01-05 --occurrences 8 --label-en "…" --label-fr "…"` |
| `GET /api/workspaces/{ws}/recurrences/{seq}` | `bk billing recurrence show` |
| `PATCH /api/workspaces/{ws}/recurrences/{seq}` | `bk billing recurrence edit`, `pause`, `resume` |
| `POST /api/workspaces/{ws}/recurrences/{seq}/generate` | `bk billing recurrence generate <seq> --period 2026-10` |

`--occurrences` is **required** on create. There is no default and no "leave it
open" — the flag not having a default is how the CLI refuses to express an
infinite series.

## The web surface

- A **recurrence card** on the invoice detail: the series label, its status, the
  frequency and start, `2/8 issued`, the next date, and the end condition stated
  in words ("stops after 8 occurrences"). The mockup's card is the layout.
- A **`↻ n/N` badge** in the invoice list on every invoice carrying a
  `recurrence_id`, including the voided one — it stays part of its series.
- **"Make recurring…"** on a one-off invoice, defaulting to 12 × monthly
  (position P13, low stakes). It opens a small form; it does not create a rule on
  one click.
- **Pause and resume**, and `paused` needs no reason (P13). If Andrea wants one,
  it is the same shape as the void reason.

## Done when

- [ ] `generate` twice for the same period produces one invoice and one **409
      naming the existing one**, and the counter advanced exactly once
- [ ] Twenty concurrent `generate` calls for the same period produce **one**
      invoice
- [ ] A voided occurrence frees its period for a replacement, and the
      replacement does **not** advance the counter a second time
- [ ] A series stops at its cap: the last `generate` sets `completed` and
      `next_date = null`, and the next call is refused with a suggestion
- [ ] A `paused` rule refuses generation and names `resume`
- [ ] A wrong `--period` is **refused**, not silently corrected
- [ ] A monthly series starting on the 31st produces the 28th or 29th in
      February and returns to the 31st in March
- [ ] A rule with `template_invoice_id = null` lists and shows without crashing —
      the completed-series case from the mockup
- [ ] The generated invoice is byte-identical in structure to a hand-made one:
      same audit shape, next number in the sequence, `draft`
- [ ] **These were watched failing, then restored:** the partial index dropped;
      `status <> 'void'` removed from it (a replacement then collides); the
      counter increment moved outside the transaction; the period check replaced
      with a substitution
- [ ] `grep -rn "cron\|setInterval\|setTimeout\|node-schedule" apps/billing`
      returns nothing on a write path

## Notes

**Finite by design, and it is a product decision rather than a simplification.**
`SCOPE.md` lists open-ended recurrence and an in-app scheduler among the explicit
non-goals. A rule that says "bill this 12 times then stop" is a thing somebody
agreed to; a rule that says "bill this monthly" is a thing nobody ever revisits.

**An occurrence is an ordinary draft.** It takes the next number from the
company's sequence, it lands in `draft`, and a human or an agent sends it like
any other. Generation is not sending, and this phase adds no way to do both at
once — a series that mailed itself would be the first thing in this app to act
on its own.

**The voided occurrence stays in its series.** `recurrence_id` is not cleared by
a void. The mockup makes the same choice and it is what lets the card say
`2/8 issued` honestly while the list shows three invoices.

**When you fix a line, ask what else is wrong with it.** The `?ref` and
`?company` fallbacks are the same class of bug as a wrong `--period`, and a found
bug makes its neighbours harder to see rather than easier. If you touch a
resolver in this phase, re-read the whole expression.
