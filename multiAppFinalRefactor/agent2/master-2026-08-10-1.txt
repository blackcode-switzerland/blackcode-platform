1. WHAT THIS PHASE IS
================================================================================
Create everything sales will need to stand on its own — and switch NOTHING over.
At the end of this phase every new table exists and is empty, no code reads them,
and both apps behave exactly as they do today. Agent 3 makes sales use them.

That ordering is deliberate. Additive-only means this phase cannot break either
app, which makes it the right place to get the shapes wrong and fix them.

**Why sales gets its own tables at all:** the refactor's contract is that the
apps share identity and nothing else. Read PLAN.md §1 if that is not obvious yet
— it is the whole point, and building these tables without understanding it
produces a copy of the shared schema rather than sales' own.

2. THE TABLES
================================================================================
All in the `sales` Postgres schema, declared in `apps/sales/lib/db/schema.ts`,
migrated through sales' OWN drizzle ledger (`apps/sales/lib/db/migrations`,
ledger schema `drizzle`, see `apps/sales/drizzle.config.ts`). D-34: a shared

  sales.invitations           workspace_id, email, role, token, expires_at, …
  sales.comments              workspace_id, parent_type, parent_id, author_id, body, …
  sales.labels                workspace_id, name, color

  sales.events                workspace_id, actor_id, action, entity_type, entity_id, …
  sales.deletion_batches      workspace_id, root_type, root_id, deleted_at, …

Take the column lists from what sales ACTUALLY uses today in the shared tables,
not from the shared tables' full definitions. Anything sales never reads is a
column you would be inheriting for no reason. `apps/sales/lib/db/queries/` and
its route handlers are the evidence; the platform tables are in
`packages/platform-db/src/schema.ts`.

Four things that are NOT free choices:

**(a) Keep `workspace_id` on every table, even though sales will only ever have
one workspace per user for now.** That column is what makes multi-workspace sales
a later UI change instead of a later migration. Dropping it because "sales has no
workspaces" would be reading the product decision as a data decision.

**(b) `parent_type` and `root_type` hold BARE nouns** — `prospect`, `meeting`,
not `sales:prospect`. The `<app>:` prefix exists in `platform.comments` because
that table is shared and had to disambiguate. Sales' own table does not.
Carrying the prefix over would be cargo-culting a workaround into the place that
made it unnecessary.

**(c) `user_id`, `owner_id`, `author_id`, `actor_id`, `uploaded_by` reference
`platform.users`.** That is correct and stays — users are shared. A cross-schema
FK to `platform.users` is exactly the boundary this refactor keeps.

**(d) Do NOT create `sales.app_access` or `sales.workspace_apps`.** Those gates
are being deleted in Phase 5, not reimplemented per app.


================================================================================
3. THE ONE SHARED-TABLE CHANGE — READ TWICE
================================================================================
This is the exception to "issues is not touched", and the only thing in this
phase that can affect production.

`platform.error_events` has a bare `workspace_id` with **no foreign key** and
**no `app` column**. That works today because there is one set of workspaces.
After Phase 3 there are two, and `workspace_id = 1` means two different things
depending on who wrote it — every error becomes ambiguous and
`bk super-admin errors` starts reporting confidently wrong workspaces.

**Expand only:**

    ALTER TABLE platform.error_events ADD COLUMN app varchar(40);
    UPDATE platform.error_events SET app = 'issues' WHERE app IS NULL;

Then make the shared `apiHandler` (`packages/platform-api/`) set it from the
`AppContext`'s app slug, so both apps populate it from now on. `SET NOT NULL`
is Phase 5's job, not yours — it cannot be safe until both apps have been
deployed writing the column.

Why the backfill is `'issues'` and not NULL: every existing row predates the
split, and issues is the only app whose workspace ids they can mean. A NULL
would be indistinguishable from "an app that forgot to set it", which is the
thing Phase 5's NOT NULL is meant to catch.

**This one needs a rollback script** in `docs/sql/`, with `\\set ON_ERROR_STOP on`
at the top. Without that, `psql` reports success after failing every statement
— CLAUDE.md findings #7 and #15.

Note it is additive and therefore safe against a running deployment: no existing
reader selects a column that did not exist. Say in your report whether you
believe that, and why.

4. VERIFICATION
================================================================================
`verify.sh` is now the instrument. From the repo root, against your LOCAL
database:

    ./multiAppFinalRefactor/verify.sh "<local url>" multiAppFinalRefactor/baseline.local-example.txt

Run it BEFORE you start and AFTER every migration. Not once at the end.

Two things about it you must internalise, from agent 1's §3:

  * **It confirms how many rows a table has, not WHICH rows.** A green verify is
    not evidence that the right thing happened.
  * **New tables must be DECLARED.** `verify.sh` fails on a table that exists in
    the database but not the baseline — that is case (d) and it is deliberate.
    Your eight new tables will trip it. Add them to the local example baseline
    and say so in your report. **Do not "fix" verify.sh to ignore new tables.**
    The production `baseline.txt` is re-captured by the human after deploy, not
    by you.

Then the gate from README §4, all of it.
