2. THE error_events CHANGE
================================================================================

** THERE ARE THREE WRITERS, NOT ONE. This is the answer to §6.4. **

The brief names `apiHandler`. Had I done only that, `error_events.app` would
have been NULL forever for a whole class of rows and Phase 5's `SET NOT NULL`
would have failed on data written AFTER the deploy — the exact condition the
NOT NULL exists to catch, produced by the migration itself.

  1. `packages/platform-api/src/handler.ts` → safeLog. Two lines: `app` in the
     column list, `${truncate(app.appSlug, 40)}` in VALUES. It already holds
     the AppContext, so nothing had to be threaded — your §6.4 worry does not
     materialise.
  2. `packages/platform-api/src/routes/telemetry.ts` → `clientErrorsRoute`,
     the client error beacon. A shared factory; only issues mounts it today,
     but sales will inherit it. Also has `app.appSlug` in scope.
  3. `apps/issues/lib/email/send.ts` → issues' own wrapper around
     `insertErrorEvent`, for failed invitation/password emails.

I did not just add `app` at three call sites. `packages/platform-db`'s
`insertErrorEvent` now REQUIRES it in its parameter type
(`Omit<NewErrorEvent,'id'|'occurred_at'|'app'> & { app: string }`), even though
the column is nullable — the nullability is about rows written by code that
predates the column, not a licence for new code to omit it. Issues' wrapper
injects `APP_SLUG` and does not accept one, so no call site in that app can
supply the wrong slug either. That is the `uploads.app` pattern verbatim, and
it is the reason that column reached 0 NULLs.

MIGRATION: `apps/issues/lib/db/migrations/0044_error_events_app.sql`, journal
idx 44. In the ISSUES ledger, not sales' — every `platform.*` migration lives
there (0037, 0041–0043), and two ledgers with independent high-water marks give
no ordering between them, so "which app's migration ran first" must not be a
question a shared column depends on. Applied locally: 327 rows, all backfilled
to 'issues', 0 NULL.

    ALTER TABLE platform.error_events ADD COLUMN IF NOT EXISTS app varchar(40);
    UPDATE platform.error_events SET app = 'issues' WHERE app IS NULL;
    CREATE INDEX IF NOT EXISTS idx_error_events_app_occurred
      ON platform.error_events (app, occurred_at);

Three things I decided that the brief did not specify:

  * The `WHERE app IS NULL` on the backfill is load-bearing, not decoration.
    It is what makes re-running the migration a no-op instead of relabelling
    sales' rows as issues'.
  * Added `idx_error_events_app_occurred`. "What has app X been throwing
    lately" is the question the column exists to answer and the one the
    super-admin Errors tab asks.
  * NO foreign key to `apps.slug`, unlike `events.app`, `uploads.app` and
    `labels.app`. Those tables hold an app's DATA, so `ON DELETE set null` is
    survivable. This one holds the record of an app FAILING, and deregistering
    an app must not erase the attribution of exactly the rows somebody is
    reading at 3am to find out what went wrong.

ROLLBACK: `docs/sql/0044-error-events-app-rollback.sql`, `\set ON_ERROR_STOP on`
at the top (watched — §4). TWO STEPS, deliberately unequal: step 1 drops the
index and is free; step 2 drops the column and ships COMMENTED OUT, because it
destroys attribution that cannot be recomputed — `workspace_id` is precisely
the value that stopped being self-describing, so there is no second source. Its
header also says the usual case needs neither: the column is additive, so a bad
deploy is a Vercel rollback and nothing here.

Also `docs/sql/sales-0003-rollback.sql`, which the brief did not ask for but
SAFETY.md's Migrations section requires of every migration. It carries the
count query that distinguishes "Phase 1, a no-op on data" from "Phase 2+, this
is data loss with a reassuring filename", and uses RESTRICT rather than CASCADE
so an unexpected dependant fails the drop instead of being taken with it.

** DO I AGREE IT IS SAFE AGAINST A RUNNING DEPLOYMENT? Yes, and here is the
   reasoning rather than the assertion, because you asked for it. **

  * No existing reader selects a column that did not exist — and I checked
    rather than assumed that no reader uses `SELECT *`: both listings
    (`listPublicErrorEvents`, `listAdminErrorEvents`) project explicit column
    lists. `getErrorEvent` DOES `select()` with no projection, i.e. `SELECT *`,
    and is still safe: it returns the whole row to a super-admin detail view,
    so an extra column is extra data, not a shape mismatch.
  * The ALTER takes ACCESS EXCLUSIVE, but a nullable column with NO DEFAULT is
    a catalog-only change in PG 11+ — no table rewrite, so the lock is held for
    microseconds rather than for a scan. **A DEFAULT would have changed this**
    on older versions and is one more reason not to add one.
  * The UPDATE does rewrite every row and takes ROW EXCLUSIVE, blocking no
    reader. 327 rows locally; production is the same order of magnitude.
  * The one genuine ordering constraint: the migration must land BEFORE the
    deploy that writes the column, never after. The code in this commit names
    `app` in its INSERT, so a deploy that reaches production ahead of the
    migration makes every error-log write fail — and safeLog SWALLOWS that, so
    the symptom is the error log silently ceasing, not an alarm. Standard
    Vercel order (postbuild migrates, then the deployment goes live) gets this
    right; it is worth not doing by hand.
