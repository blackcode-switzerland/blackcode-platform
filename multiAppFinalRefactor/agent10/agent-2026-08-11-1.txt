1. `packages/platform-email` — WHAT MOVED, WHAT AN APP SUPPLIES, WHAT A KEYLESS
   APP DOES
================================================================================

1.1 WHAT MOVED. All three files — `client.ts`, `send.ts`, `templates.ts` (392
    lines) — out of `apps/issues/lib/email/`. What is left in each app is a
    BINDING, not a module: `apps/<app>/lib/email/send.ts`, ~20 lines, which is
    the only place an app's identity and database meet the sender. Everything
    else imports from the binding, never from the package — the `@/lib/storage`
    rule, for the `@/lib/storage` reason.

1.2 WHAT AN APP SUPPLIES. **A four-field identity, and NOT a palette and NOT a
    template set.** This was the open design question agent 8 refused to answer
    in a margin (§5.3) and that your §3a did not decide, so I decided it and
    wrote the argument into `packages/platform-email/src/identity.ts` where the
    next person will look:

        name          the display name — `Blackcode Issues`, `b/sales`.
                      Read from each app's `APP_NAME`, so the From line and the
                      UI cannot drift apart
        appUrl        the origin the logo is loaded from, and nothing else
        accent        the primary button fill
        contactEmail  the reply-to in the footer

    Plus `app` (the slug, for `error_events.app`) and `getDb` (lazy).

    The reasoning, compressed: `BRAND` appeared FIVE times in the old
    templates — From line, header wordmark, invitation body, reset subject,
    footer — so "which app is this from" was never just `fromAddress()`, which
    is what your §3a assumed. But it is still only four FACTS. A palette input
    would be four more values that are contrast-tuned against each other for a
    light-only email, and **nothing in this repo renders an email**, so an app
    could ship unreadable mail and no check would see it. `accent` is safe alone
    because it only ever carries white text on a solid fill. A per-app template
    set is the copy `adding-an-app.md` item 8 exists to forbid, with extra steps.

    Your §3b's "each app's own visual language" is a rule about SCREENS. An
    email is a 520px light-only card that has to survive Outlook's Word engine;
    there is no visual language in it beyond the wordmark and the button.

1.3 WHAT A KEYLESS APP DOES — AND THIS IS THE PART THAT IS NOT A MOVE.
    `emailEnabled()` already existed and was ALREADY the silent failure you
    objected to: the routes called it, got `{sent:false}`, and returned
    `{ok:true}` anyway. So "an app without a key must degrade honestly" was new
    behaviour, not a promotion.

        canDeliverEmail()  ≠  emailEnabled()

    `canDeliverEmail()` is `emailEnabled() || NODE_ENV !== 'production'`, and
    the carve-out is deliberate: outside production the OTP is printed to the
    server log, where the only person who could read that mailbox is already
    looking. Refusing there would make the reset flow untestable locally without
    a Resend account, which is worse than the thing the rule prevents.

    In production, a deployment that cannot deliver answers
    **503 `email_not_configured`** with a `suggestion` naming both variables —
    and answers it BEFORE minting an OTP or spending a rate-limit slot. That
    ordering is the actual requirement: a route that minted a code, burned a
    slot, invalidated the caller's prior pending codes and THEN refused would be
    worse than the bug, because the person who later sets the key finds
    themselves already rate-limited by requests that never sent anything.
    Guarded, and the guard watched to fail on exactly that mutation — §4.

1.4 ONE THING I DID THAT YOU DID NOT ASK FOR, because it deletes a copy rather
    than creating one. `/api/auth/password-reset/{request,confirm}` are now
    SHARED FACTORIES (`publicPasswordResetRequestRoute` / `…ConfirmRoute`).

    `packages/platform-api/src/routes/password.ts` used to say the logged-out
    pair "is not here — everything under /api/auth is per-app by design". The
    ROUTES still are: each app mounts them under its own `app/api/auth/`. Their
    BODIES are not, because writing sales' pair by hand would have produced two
    OTP policies — which digits are accepted, which failure maps to which code,
    what a person reads when a code expires — against ONE shared credential.
    `platform-auth`'s own header says the weakest app then sets the real floor.

    This touches `apps/issues`' production routes. Behaviour and response bodies
    are unchanged; verified by curl against both apps and in the browser (§3.6).

4. HOW I TOLD "NOT SENT" FROM "NOT YET" — DECIDED BEFORE TESTING
================================================================================

4.1 THE INSTRUMENT: **Resend's own API**, `GET /emails` and `GET /emails/{id}`,
    authenticated with the key already in `apps/issues/.env.local`.

    I established it BEFORE sending anything, and I established that it could
    see the PRESENCE of what I would later claim was absent:

      - it listed 8 pre-existing messages with a baseline timestamp
        (2026-08-10), so a new row is unambiguous
      - `last_event` discriminates: the existing rows included both
        `delivered` AND one `bounced` from 2026-08-04. An instrument that only
        ever prints "delivered" cannot tell me anything; this one had already
        recorded a failure
      - it carries `from`, so it also proves WHICH identity sent — which turned
        one observation into two facts (§3.7)
      - it carries `text` and `html`, so I could read the OTP out of the message
        that was actually delivered rather than out of the database or a log

    So the three states are distinct and none of them is an absence I inferred:
        not sent  → no new row at all
        not yet   → a row exists, `last_event` is not yet `delivered`
        arrived   → a row exists with `last_event: delivered`
        failed    → a row exists with `last_event: bounced`

    Every email in §3 was confirmed `delivered` before I called it arrived. Six
    messages left during this phase (8 → 14).

4.2 THE OTHER INSTRUMENT PROBLEM — AND THIS ONE BIT ME.
    For the browser I polled the DOM **inside a single `evaluate`** rather than
    sampling between tool calls, because agent 7's false "silent no-op" came
    from a driver whose round-trip is slower than a 4-second toast. That worked.

    But I designed sales' error surface as a persistent `role="alert"` element
    rather than a toast, which is why the refusals in §2.6 and §3.6 are
    observable at all. Worth stating as a design consequence and not luck: a
    failure a person must be able to act on should not be rendered in something
    that disappears.
