1. WHY THIS PHASE EXISTS
================================================================================
`apps/issues` is live and people are using it. Later phases delete rows — sales'
rows, from tables issues also writes to. The difference between "deleted sales'
374 rows" and "deleted 374 rows" is invisible unless something is counting.

So: a baseline of what is in the database now, and a script that re-checks it
after every step. That script is the only thing standing between this refactor
and losing somebody's comments.

**It is also the single most likely thing in this whole project to be green and
inert.** Read the guardrail table in CLAUDE.md before you start. Nineteen checks
in this repo have been found reporting success over nothing, and #5 and #16 are
the two shapes you are most at risk of:

  #5  `bk __routes` deduped rows, so two things collapsed into one and the
      second appeared not to exist — a check that silently measured less than
      it claimed
  #16 a probe whose every "denial" was satisfied by a role that had been granted
      nothing at all — it could not tell a working boundary from an absent one

Your script's version of #16 is: **it finds no tables, compares nothing, and
exits 0.** Design against that from the first line.


================================================================================
2. WHAT TO BUILD
================================================================================
All of it under `multiAppFinalRefactor/`. Shell + SQL. No new npm dependencies.

--- 2a. capture-baseline.sh -----------------------------------------------------
Takes a connection URL. Writes a machine-readable baseline file.

Per table, in schemas `platform`, `issues` and `sales`, record MORE than a count.
A count alone cannot tell "5 rows deleted" from "5 deleted and 5 inserted", and
the second is exactly what a mid-refactor bug looks like:

    schema.table    count    min(id)    max(id)

`min(id)` is the important one — it catches old rows disappearing even while new
ones arrive. If a table has no integer `id`, say so in the file rather than
skipping it silently; a skipped table is a table nobody is watching.

Also record, at the top: the timestamp, the database name, and the number of
tables found. That last number is what makes vacuity detectable.

--- 2b. verify.sh ---------------------------------------------------------------
Takes a connection URL and a baseline file. Re-measures, diffs, prints per-table
PASS/FAIL, exits non-zero on any problem.

It must FAIL, loudly and by name, on every one of these:

  (a) a count DECREASED and the decrease was not declared        ← the main event
  (b) `min(id)` INCREASED — the oldest row is gone
  (c) a table in the baseline is MISSING from the database
  (d) a table in the database is MISSING from the baseline       ← new table, undeclared
  (e) the number of tables found is 0, or differs from the baseline's header
  (f) the connection failed, or psql returned nothing

(e) and (f) are the ones that matter most and are easiest to leave out. A script
that cannot connect and prints no failures has passed, and that is finding #16
reproduced in a shell script.

**Increases are NOT failures.** People are using issues while this refactor
happens; comments and events will grow. Print them as INFO.

--- 2c. Declared decreases ------------------------------------------------------
Phase 3 deliberately deletes sales' rows from shared tables. Those decreases are
expected, and the rule from SAFETY.md is that they are **declared before they
happen, never explained afterwards**.

Design the mechanism. My suggestion, take it or better it: a block in the
baseline file like

    # EXPECTED 2026-08-12 phase-3 agent4
    # platform.comments -8   sales rows, parent_type LIKE 'sales:%'

...which verify.sh reads, so a decrease of exactly 8 passes with a note naming
the declaration, and a decrease of 9 fails. **An undeclared decrease must never
pass**, and a declaration must not be a blanket "ignore this table".

--- 2d. backup.sh (thin) --------------------------------------------------------
A wrapper around the `pg_dump` invocation in SAFETY.md, so nobody retypes it.
Must refuse to run without a destination path, and must verify the dump file is
non-empty afterwards. `pg_dump` exiting 0 having written nothing useful is the
same family of failure as everything else in this brief.

Do NOT script the Neon branch step — that is the human's dashboard work and
there are no credentials here.

output, restore. Then do the harder half:

  **Ask what your script would STILL pass on, and inject that.**

Some candidates. Find your own too, and say which you tried:
  - delete a row from the MIDDLE of a table (count drops, max(id) unchanged)
  - delete a row and insert a new one (count identical — does min/max catch it?)
  - point verify.sh at an empty database that has the right schemas and no rows

**If something you expected to be caught was not, say so and either fix it or
