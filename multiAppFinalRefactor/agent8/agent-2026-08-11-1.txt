1. THE `deleteAccountReport` BUG — WHAT IT DOES, OBSERVED
================================================================================
Your §1 is right that it reads `platform.workspaces` and cannot see sales. What
it gets wrong is the CONSEQUENCE, and the correction matters because it changes
what §2d has to be.

** YOU WROTE: "A person with a sales workspace and no issues workspace gets a
   report saying there is nothing to lose." **

That is the harmless half. Here is the whole thing, measured.

1.1 WHAT I OBSERVED. I made a real account through the real register route, gave
    it one issues workspace (the register route mints it) and one sales
    workspace, signed in, and asked the live dry-run:

      DELETE /api/me?dry_run=true
      -> {"blocked_by":[],
          "will_hard_delete":[{"workspace_id":305,"name":"Agent 8's Workspace"}]}

    One workspace named. `sales.workspaces` id 1024, and everything in it, is
    not mentioned, not counted, and not hinted at. **The report is not empty —
    it is confidently incomplete**, which is worse than empty: an empty report
    invites suspicion and a partial one reads as authoritative.

1.2 ** AND THEN THE DELETE DOES NOT DELETE IT. ** This is the part your brief
    does not have, and I checked the catalog rather than the code:

      sales.workspaces.owner_id -> platform.users.id   ON DELETE RESTRICT

    `softDeleteUser` is a SOFT delete — an UPDATE setting `deleted_at`,
    `password_hash = NULL`, `google_id = NULL`. **An UPDATE does not fire a
    delete rule.** So RESTRICT never engages, nothing refuses, nothing cascades,
    and the sales workspace survives in full: prospects, meetings,
    communications, documents — owned by an account that can no longer
    authenticate by password or by Google, whose tokens have been revoked.

    So the failure is not "data lost". It is **data STRANDED**: retained,
    invisible to its owner, unreachable by anyone, and not reported at any point
    in the flow. It is also not recoverable by the person — there is no sign-in
    left to recover with.

1.3 WHY THAT CHANGES THE DESIGN. Your §2d item 3 says "'this app only' while
    other apps still hold data does NOT delete the account". Correct. But 1.2
    means the CURRENT "all apps" path does not delete all apps either — it
    deletes issues and abandons the rest. So §2d is not only a new choice added
    in front of an existing correct operation. **The existing operation is
    itself wrong, and both branches of the new UI need building on something
    that works.** A phase that only added the chooser would ship a screen
    offering "all apps" that still means "issues, and then silence".

1.4 WHAT I DID NOT DO, AND WHY NOT. I did not ship a partial fix. The obvious
    small one — route the report through `app.workspaces` instead of naming
    `platform.workspaces` — is a no-op for the only app that serves this route:
    `apps/issues` IS `platform.workspaces`, so the report would be
    byte-identical and the bug untouched. It would show up in a diff as "fixed
    the app-scoping bug" and change nothing. That is precisely the shape
    CLAUDE.md's standing rule is about, so I left the code alone and wrote the
    finding down as PLAN.md §9 item 8 instead.

    `apps/sales` does not serve `DELETE /api/me` at all (agent 3's decision,
    argued in `apps/sales/app/api/me/route.ts`, and it is a good one). Note that
    §2d's "this app only" contradicts it: sales will need SOME deletion route.
    See §2.4.

2. §2d — THE MECHANISM, AND WHY THE ALTERNATIVES LOSE
================================================================================
Your §6.1: "I do not know how an app should learn what another app holds." Here
is the answer, with the premise verified rather than assumed.

2.1 THE CHOICE: ** a server-side HTTP fan-out over `platform.apps.base_url`,
    forwarding the caller's own session cookie, with reachability reported as a
    first-class value. **

    The deployment answering `DELETE /api/me` reads the address book, and for
    each OTHER app calls that app's own `GET /api/me/footprint`, passing the
    `Cookie` header it already received. Each app answers only for itself, from
    its own tables, under its own Postgres role. Nothing shared is added.

2.2 THE PREMISE, CHECKED. This works only if one credential is valid at both
    origins, so I read it rather than assuming it:

      - the session cookie is renamed and domain-widened by
        `packages/platform-auth/src/session-cookie.ts` (D-16). I saw it live:
        the cookie is `blackcode.session-token`, not `next-auth.session-token`.
      - in production it carries `Domain=.blackcode.ch`, so the browser sends it
        to whichever app the person is on, and that app's SERVER therefore holds
        a credential valid at the other.
      - `apps/sales/.env.local` documents that `NEXTAUTH_SECRET` is deliberately
        the same value, so sales can decrypt a cookie issued by issues.

    ** THE ONE THING THAT DOES NOT HOLD LOCALLY: ** with `NEXTAUTH_URL` on
    `localhost`, the module deliberately emits NO `Domain` attribute — that is
    the documented default and it is what keeps localhost and `*.vercel.app`
    previews working. So the fan-out is not exercisable in local dev the way it
    runs in production, and Phase 9 must not conclude "it works" from a local
    pass. That is the same class of mistake as agent 7's toast.

2.3 WHY IT CANNOT SILENTLY REPORT "NO DATA" — your explicit constraint, and the
    entity-drift failure (CLAUDE.md #14) restated. The answer is a TYPE, not a
    convention. Each entry is one of:

        { app: 'sales', reachable: true,  holds: {...} }   -- it answered
        { app: 'sales', reachable: false, error: '...' }   -- it did not

    There is no third shape and no default, so "no data" and "no answer" cannot
    collapse into each other. Two rules follow, and they are the whole safety
    property:

      - the UI RENDERS the unreachable ones, by name, as unknown. Not omitted,
        not zero.
      - ** "all apps" is REFUSED while any app is unreachable **, with a 409
        naming which. An irreversible operation may not run on a partial census.
        "This app only" is still allowed, because it is answerable locally and
        needs no census at all.

    That last split is your §6.1's own guess, and it is right: **only the LIST
    needs the fan-out.** The destructive action for one app never leaves that
    app.

2.4 WHAT ELSE THE MECHANISM DRAGS IN, so Phase 9's brief can be honest:
      - `apps/sales` must serve a deletion route after all — a NARROW one
        ("delete my data in this app"), not `DELETE /api/me`. Agent 3's argument
        was against two deployments each offering full account closure, and that
        argument survives intact: full closure stays issues-only.
      - both routes inherit `DELETE /api/me`'s parity exclusion and its reason.
      - `platform.apps.base_url` becomes load-bearing for a destructive
        operation for the first time. A wrong or stale `base_url` currently
        makes `bk` fail visibly; here it would make an app look unreachable,
        which now BLOCKS deletion — a safe direction, worth stating.
      - the footprint route must answer for a person who is not a member of
        anything in that app, and "you have nothing here" must be distinguishable
        from "you are not known here". Same distinction as `/api/meta`'s
        `workspaces: []`.

2.5 WHY THE ALTERNATIVES LOSE.

    (a) A SHARED `platform.account_footprint` TABLE each app maintains.
        Rejected. It is `platform.entities` again — a projection that drifts,
        needing a reconciler that cannot be written, because the reconciler
        would have to read every app's tables and no role may. It would answer
        instantly and be wrong silently, which is the exact failure mode you
        told me to avoid, arrived at from the other direction.

    (b) A CALLBACK ON `AppContext`. Rejected, and it is a category error worth
        naming: `AppContext` is what THIS deployment supplies about ITSELF. A
        callback there could only ever answer for the app already answering. It
        does not cross the boundary; it just looks like it does.

    (c) A BROWSER-SIDE FAN-OUT (the page fetches each app directly). Tempting —
        the cookie is already in the jar. Rejected: cross-origin credentialed
        requests need each app to return `Access-Control-Allow-Credentials` and
        an explicit origin allowlist, i.e. every app must grow CORS it does not
        otherwise need, and a CORS misconfiguration is a security surface added
        to serve a delete-account screen. It also puts the census in the least
        trustworthy place — a client that can simply omit an app it does not
        like the answer from.

    (d) MAKE THE FK ACTUALLY FIRE (`softDeleteUser` -> hard delete). Rejected
        loudly. `ON DELETE RESTRICT` would then REFUSE the account closure, and
        the twelve `ON DELETE CASCADE` FKs on `platform.workspaces` mean the
        neighbouring paths would silently take content with them. PLAN.md's
        deploy note already says not to reach for the FK layer to fix an
        application-layer question.

2.6 ONE THING I COULD NOT SETTLE, and it is a product decision, not a technical
    one. "This app only, and it is the LAST app" — the person has data nowhere
    else. Is that a full account closure, or does it leave an identity with no
    tenancy anywhere? Your §2d says "this app only … does NOT delete the
    account", which taken literally leaves an account that exists, can sign in,
    and can reach nothing. I think that is right (the account is the shared
    thing; deleting it is a separate, louder act) but it should be DECIDED
    rather than fallen into, because it is what a person will hit most often —
    almost everybody is in exactly one app.
