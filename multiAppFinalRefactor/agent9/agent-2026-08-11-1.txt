2. THE STRANDING BUG — WHAT CLOSES IT
================================================================================
Agent 8's mechanism, implemented as specified. I did not replace it and I have
no quarrel with it. What follows is what it cost and where it was wrong.

2.1 THE SHAPE
    - `AppContext.footprint`, REQUIRED — `{ read(userId), purge(userId) }`.
      Supplied by issues, sales and the scaffold. Required is the whole safety
      property: an app that cannot answer is an app the account close silently
      SKIPS, which is this bug as a default. An app holding nothing per person
      answers `UNKNOWN_FOOTPRINT` explicitly; silence is not an answer.
    - `GET/DELETE /api/me/footprint`, one shared factory, mounted by all three.
      Session-only by construction (`requireSessionResolver`), so neither method
      is reachable from `bk` — an honest exclusion rather than a convenient one.
    - `accountCensus` fans out over `platform.apps.base_url` forwarding the
      caller's `Cookie`. `AppCensusEntry` is a discriminated union:
      `{reachable:true, footprint}` | `{reachable:false, error}`. No third
      shape, no default, and the unreachable shape HAS NO FIELD that could hold
      a zero — so the UI cannot render "nothing" for an app it could not ask
      without failing to compile.
    - `DELETE /api/me?scope=all_apps`. `scope` is REQUIRED; a bare call is a 400
      with a suggestion. The route's meaning widened to reach every app, and an
      irreversible operation that quietly starts doing more is the wrong place
      for a default. One caller, so the break costs one line.
    - **The ORDER is the recovery story.** Every other app is purged first,
      sequentially; `platform.users` is touched LAST. The worst partial failure
      is "one app emptied, account still works, error names the app that
      failed". The inverse order is this phase's bug, reintroduced inside the
      fix. `purge` returns a FRESH read and the caller asserts it is empty
      rather than trusting the 200 — finding #16.

2.2 ** RESTRICT SURVIVES, AND STAYS INERT — YOUR §5.1 ** ("It is currently
    inert — a constraint that cannot fire is a comment.")

    You are right that it cannot fire, and I kept it anyway. Three reasons, and
    the reasoning is now written ON THE COLUMN in `apps/sales/lib/db/schema.ts`
    rather than in a reply nobody will read again:

      - it is CORRECT for the one case it can see, a genuine hard
        `DELETE FROM platform.users`. Dropping it swaps an inert guard for none.
      - making the delete hard so it CAN fire is agent 8's §2.5(d), rejected
        loudly and still right: RESTRICT would then REFUSE the closure outright,
        and the twelve `ON DELETE CASCADE` FKs on `platform.workspaces` would
        take issues' content with it.
      - the real fix belongs in the application layer, and now IS there.

    What I would not accept is leaving it looking like protection. The column
    now says, in the file somebody reads before changing it, that it cannot fire
    against an UPDATE, that it is NOT what makes account closure safe, and what
    is. That is the honest version of "a constraint that cannot fire is a
    comment": make it a comment that tells the truth.

2.3 ** WHERE AGENT 8 — AND THEREFORE YOUR BRIEF — WAS WRONG. THIS IS THE ONE. **

    Agent 8's §2.4, quoted into your §2 as settled:

      > "A wrong or stale `base_url` currently makes `bk` fail visibly; here it
      > would make an app look unreachable, which now BLOCKS deletion — a safe
      > direction, worth stating."

    ** IT IS NOT A SAFE DIRECTION. ** It is safe only for an address that
    answers nothing. An address pointing at ANOTHER APP IN THE SUITE answers
    confidently, as that app.

    MEASURED, not reasoned about. I set `sales.base_url` to the issues
    deployment and asked for the census:

      Blackcode Issues     reachable=True  [{'label': 'issues', 'count': 2}]
      Sales                reachable=True  [{'label': 'issues', 'count': 2}]

    Two apps, one set of data, reported twice under two names, `reachable: true`
    both times, no warning anywhere. `?scope=all_apps` would then have purged the
    issues origin TWICE, read issues' own "I am empty" as sales' answer, asserted
    the census satisfied, and closed the account over an untouched sales
    workspace. **This phase's own bug, reached through a config error, past every
    guard I had written for it.**

    I found this by asking the standing rule's second question — "what would this
    still pass on?" — not by review, and not by any test. It was green.

    THE FIX: every app already names itself in its reply (`{ app, footprint }`),
    so the check is free. Both the census and the purge now reject an answer
    whose `app` is not the app they addressed, which turns the config error back
    into `reachable: false` and refuses the close. Re-measured:

      Sales   reachable=False   answered as "issues" — its base_url in
                                platform.apps points at the wrong deployment

    It matters MORE on the purge than on the census, and that path is checked
    too: by the time a purge answers, it has already deleted something.

2.4 YOUR §5.2 — "what does 'delete that app's data' mean for a workspace they
    SOLELY own: delete it, or orphan it to nobody?" You guessed the split might
    already answer it. It does: delete it. A solely-owned workspace is theirs to
    destroy, which is `deleteAccountReport`'s existing rule, and I extended that
    rule rather than replacing it — a workspace with OTHER MEMBERS blocks, in
    whichever app it is in. Orphaning was never a real option: an ownerless
    workspace is a row with a NOT NULL `owner_id` and nobody who can administer
    it.

    The interesting half is that the block now CROSSES APPS. A sales workspace
    with a second member in it refuses the whole-account close from issues, by
    name, and I watched all three refusals (§3, case 5).

2.5 YOUR §5.3 — "per-app route or a factory?" A FACTORY, plus a per-app
    `FootprintSource`. The route is identical everywhere ("who is asking, what
    do you hold, delete it"); only the ANSWER is app-shaped, and `holds` is a
    free-form `{label, count}[]` so the platform never decides what a future app
    is allowed to hold. Note this is NOT agent 8's rejected §2.5(b): it rejected
    an AppContext callback as a way to learn about ANOTHER app, which is a
    category error. This is an app describing ITSELF, which is exactly what
    AppContext is for.

2.6 AGENT 8'S §2.6, WHICH IT ASKED TO HAVE DECIDED — "this app only, and it is
    the LAST app". ** DECIDED: "this app only" NEVER closes the account, ever. **

    Not a taste call. The moment it depends on whether other apps hold data, it
    needs the census — and then an unreachable app either blocks the one
    operation that was always meant to be locally answerable, or silently
    promotes a scoped delete into a full account closure. Both are worse than an
    account that exists and reaches nothing. The screen says so in the option
    text ("Your account stays open and you can sign in again"), so it is chosen
    rather than fallen into.

    Reversible if you disagree: it is one branch, and the census is already
    there. But it should be reversed deliberately, not because it looks tidier.

did not prove the production one.

SO WHAT PRODUCTION MUST SHOW — three things, and only the first is load-bearing:

  1. ** A REAL CENSUS ACROSS THE TWO SUBDOMAINS. ** Sign in on
     issues.blackcode.ch with an account that has a sales workspace, open

  2. `platform.apps.base_url` is correct for BOTH rows in production. It is now
